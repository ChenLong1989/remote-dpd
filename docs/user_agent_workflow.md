# 用户-Agent 协作流程

**适用范围**: 项目需求变更、设计文档更新、代码实现、PR 与合入后的收尾  
**核心入口**: `docs/current_plan.md`

---

## 1. 目标

本文档定义用户与 Agent 在本项目中推进一次改动的标准流程。

原则：

- `docs/current_plan.md` 是当前改动的主入口，记录用户意图、Agent 计划、执行状态和收尾记录。`docs/current_plan.md`作为临时文件维护在本地，已添加进.gitignore。
- 设计文档用于描述稳定设计；临时讨论只用 `[USER]` 和 `[AGENT]` 标记承载。
- 代码实现必须在用户批准计划和文档改动后开始。
- 实现完成后，设计文档必须回到干净状态：去掉 `[USER]` / `[AGENT]`，并与代码重新对齐。

---

## 2. 改动流程

### 2.1 用户描述改动意图

用户先在 `docs/current_plan.md` 中描述本次改动的目标、背景、约束和验收方式。

如果某个意图需要落在具体设计位置，用户可以在相关设计文档中用 `[USER]` 标签补充细节：

```markdown
[USER] 希望这里支持异步保存，避免采集主循环被 HDF5 写入阻塞。
```

`[USER]` 可以出现在模块设计文档或系统设计文档中。用户只需要描述“想要什么”和“为什么”，不需要写正式设计。

### 2.2 Agent 制定计划和设计草案

Agent 理解用户意图后，先做计划，不直接改代码。

Agent 需要完成：

1. 阅读 `docs/current_plan.md`、相关 `[USER]` 标记、受影响设计文档和必要代码。
2. 在 `docs/current_plan.md` 中追加详细实现计划，包括影响范围、执行顺序、验证方式和已知风险。
3. 在受影响模块的设计文档中用 `[AGENT]` 标签写出拟议设计；如果影响跨模块边界，则同步更新 `docs/system_design.md`。
4. 对不确定事项明确列出问题或假设，等待用户确认。

`[AGENT]` 示例：

```markdown
[AGENT] 拟新增 `save_async()` 作为异步保存入口；保留 `save()` 作为同步兼容入口，
内部复用同一个 `_save_sync()` 实现。实现阶段将补充采集路径测试。
```

### 2.3 用户 Review 和批准

用户 review `docs/current_plan.md` 和设计文档中的 `[AGENT]` 草案。

在用户明确批准前，Agent 只能继续修改计划和文档草案，不得开始代码实现。用户可以要求 Agent 反复调整计划、拆分范围、改变设计或补充风险说明。

进入实现阶段需要明确批准，例如：

```text
批准，按这个计划实现。
```

### 2.4 Agent 实现并正式更新文档

获得用户批准后，Agent 才开始代码实现。

实现阶段需要同步完成：

1. 按已批准计划修改代码、配置、脚本和测试。
2. 运行与改动范围匹配的验证。
3. 正式更新受影响设计文档，去掉所有本次改动相关的 `[USER]` 和 `[AGENT]` 标签。
4. 确保设计文档描述的是最终实现，而不是讨论过程。
5. 提交 PR，并在 PR 说明中列出实现内容、验证结果和未覆盖风险。

正式文档不保留“用户想要”“Agent 拟议”这类临时语句；它只描述当前系统真实设计。

### 2.5 用户 Review 实现并合入

用户 review PR 中的代码、文档和验证结果。

如需修改，Agent 按用户意见继续迭代代码和文档，直到用户批准合入。合入前，文档和实现必须一致。

### 2.6 Agent 收尾

PR 合入后，Agent 负责收尾：

1. 清理已合入的工作分支。
2. 本地同步到最新 `main`。
3. 在 `docs/current_plan.md` 中记录最终状态、合入信息、验证结论和遗留事项。

收尾记录应简洁，便于下一次改动开始时快速判断项目状态。

---

## 3. 文件职责

| 文件 | 职责 |
|------|------|
| `docs/current_plan.md` | 当前改动入口；记录用户意图、Agent 计划、执行记录和收尾状态 |
| `docs/system_design.md` | 系统级架构、跨模块边界、全局设计约束 |
| `docs/user_agent_workflow.md` | 本流程文档 |

---

## 4. 标签规则

只使用两个临时标签：

| 标签 | 使用者 | 用途 | 清理时机 |
|------|--------|------|----------|
| `[USER]` | 用户 | 描述改动意图、背景、约束或验收期望 | 实现完成并正式更新文档时删除 |
| `[AGENT]` | Agent | 描述拟议设计、实现计划、风险或待确认问题 | 实现完成并正式更新文档时删除 |

---

## 5. Agent 工作要求

### 5.1 计划阶段

Agent 必须先产出可 review 的计划和设计草案。计划至少包含：

- 目标理解。
- 受影响文件或模块。
- 实现步骤。
- 验证方式。
- 风险、假设和需要用户确认的问题。

### 5.2 实现阶段

Agent 只能在用户批准后实现。实现时应遵守：

- 优先保持向后兼容；若无法兼容，必须在计划和 PR 中说明。
- 代码、配置、测试和设计文档一起更新。
- 不把 `docs/current_plan.md` 中的阶段编号、临时背景或讨论内容写入代码。
- 如果发现已批准计划不可行，暂停实现，回到计划阶段让用户确认调整。

### 5.3 文档收敛

实现结束后，设计文档应满足：

- 没有本次改动遗留的 `[USER]` / `[AGENT]`。
- 接口、参数、配置、数据格式和行为与代码一致。
- 只保留稳定设计，不保留过程性讨论。

---

## 6. 常见情况

### 6.1 用户只改了 `docs/current_plan.md`

Agent 仍应检查是否需要同步设计文档。如果改动影响接口、数据结构、模块边界或长期设计，Agent 应在计划阶段补充相应 `[AGENT]` 设计草案。

### 6.2 发现文档和代码已经不一致

Agent 应在计划中说明不一致点，并提出对齐方案。实现阶段完成后，以最终代码和正式设计文档一致为准。

### 6.3 改动跨多个模块

Agent 应在 `docs/current_plan.md` 中写清楚跨模块执行顺序，并在必要时更新 `docs/system_design.md` 的 `[AGENT]` 草案。

---

**文档结束**

所有项目改动都应遵循：用户写意图 → Agent 写计划和设计草案 → 用户批准 → Agent 实现并清理文档 → PR review 合入 → Agent 收尾。
